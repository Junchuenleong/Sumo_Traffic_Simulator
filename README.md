# Multi-Agent Traffic Signal Control with Emergency Vehicle Preemption

A multi-agent PPO controller for urban traffic signal control in SUMO, with a hybrid rule-based override for emergency-vehicle preemption. The pipeline is validated end-to-end on a synthetic 4×4 grid, then evaluated on a Semenyih (Malaysia) sub-network imported from OpenStreetMap.

## Highlights

- **~84 % reduction** in average vehicle waiting time vs. the fixed-time baseline (101.6 s → 16.2 s) on the real-world `offpeak` scenario.
- **0.0 s** mean emergency-vehicle waiting time — preemption clears the path end-to-end.
- **Vehicle-centric EMV detection** via `traci.vehicle.getNextTLS()` — route-aware, not lane-based, which matters on OSM-imported networks with short TLS-controlled lane stubs.
- **Parameter-shared PPO** across all N traffic lights — one policy file controls the whole network.
- **Two-tier validation**: synthetic grid first (less complex routing, easier visualisation for changes made), then the real city. If something is wrong with the implementation, grid allows easier spotting for mistakes before running on real city.

> 💡 **Looking for a specific command?** See [`COMMANDS_CHEATSHEET.md`](COMMANDS_CHEATSHEET.md) for a copy-paste reference of every pipeline command, GUI flags, diagnostic switches, and common workflows.

## Two-tier validation strategy

The repo supports two networks and you should run them in this order:

1. **Synthetic 4×4 grid** (`networks/grid.net.xml`) — generated by `generate_grid_scenario.py`. Deterministic topology, identical TLS programs, fast to simulate. Used to confirm the controllers, the reward shaping, the EMV preemption logic, and the PPO training loop all behave as expected before you commit to a real-world run. PPO should beat fixed-time and MaxPressure on this network easily; if it doesn't, something is broken upstream.
2. **Semenyih sub-network** (`networks/multi_agent_clean.net.xml`) — a real urban grid imported from OSM via osmWebWizard. This is the network used for every number in the Results table below. Train here only after the grid run looks sane.

### Tier isolation

Outputs from the two tiers are kept in fully separate directories so a grid run can never overwrite a real-world result (or vice versa):

```
scenarios/grid/    scenarios/real/
outputs/grid/      outputs/real/
models/grid/       models/real/
```

Selecting between them is a single environment variable: `TSC_TIER=grid` or `TSC_TIER=real`. `Config()` reads it on construction and routes every path — including the `.net.xml` file — through the right tier folder. Both pipeline scripts (`run_all_grid.bat` / `run_all.bat`) set it for you; you only need to set it manually when running individual commands. Default if unset: `real`.

The tier-to-network mapping lives in `_TIER_NETS` at the top of `config.py`. To use a different real-network file (e.g. for a different OSM city), edit the `"real"` entry there — that's the one place.

## Installation

1. **Install SUMO** — version 1.19 or newer. Set `SUMO_HOME`:
   - Windows: `set SUMO_HOME=C:\Program Files (x86)\Eclipse\Sumo`
   - Linux/macOS: `export SUMO_HOME=/usr/share/sumo`

2. **Python environment** (Python 3.10+):
   ```bash
   python -m venv .venv
   source .venv/bin/activate          # Windows: .venv\Scripts\activate
   pip install -r requirements.txt
   ```

3. **Sanity check** (uses the synthetic grid, finishes in seconds):
   ```bash
   set TSC_TIER=grid                                            # PowerShell: $env:TSC_TIER="grid"
   python generate_grid_scenario.py --scenario offpeak
   python run.py fixed --scenario offpeak
   ```
   If that runs to completion and writes `outputs/grid/fixed_offpeak_tripinfo.xml`, you're set.

### Caveats

- **The bundle covers `offpeak` only** — that's the headline scenario behind the Results table. Rushhour and gridlock are heavier (~8 h on the real net for rushhour) and aren't included; if you want them, they need to be retrained locally with `run_all.bat rushhour` or `run_all_grid.bat rushhour`.
- **One model per tier.** `models/real/ppo_shared_final.zip` is whichever scenario was most recently trained on that tier. Running `python run.py train --scenario rushhour` in the same tier will **overwrite** the offpeak model from the bundle. If you want to keep both, rename the existing one first:
  ```bat
  ren models\real\ppo_shared_final.zip ppo_shared_final_offpeak.zip
  ren models\real\vecnormalize.pkl    vecnormalize_offpeak.pkl
  ```
  Then load the renamed model later with `python run.py ppo --scenario offpeak --emv --model models/real/ppo_shared_final_offpeak`.
- The bundle is `.gitignore`d on purpose — files are too large for the repo and would bloat git history. OneDrive is the canonical source.

## Network setup

You can run the pipeline on either the synthetic grid (recommended for a first pass) or a real OSM-imported city. Pick one and set `TSC_TIER` accordingly — no `config.py` edits are needed for the default real-network filename.

### Option A — Synthetic grid (recommended first)

`generate_grid_scenario.py` builds an N×N grid network plus matching background-traffic and EMV route files. All output paths follow `config.py`'s tier-aware layout, so generated files plug straight into `Config(tier="grid")` with no extra wiring.

```bash
set TSC_TIER=grid

# Default 4x4 grid, offpeak demand:
python generate_grid_scenario.py --scenario offpeak

# Other demand levels (heavier insertion rates):
python generate_grid_scenario.py --scenario rushhour
python generate_grid_scenario.py --scenario gridlock

# Larger grid:
python generate_grid_scenario.py --size 6 --scenario offpeak
```

This writes:
- `networks/grid.net.xml` — auto-picked when `TSC_TIER=grid`
- `scenarios/grid/<scenario>.rou.xml`
- `scenarios/grid/emv.rou.xml`
- `scenarios/grid/emv_types.add.xml`

That's it — just run the rest of the pipeline:

```bash
python run.py fixed --scenario offpeak --emv
python run.py train --scenario offpeak --emv --timesteps 500000
```

### Option B — OSM-imported real city

The repo ships with `networks/multi_agent_clean.net.xml` — a pre-built Semenyih sub-network. It's the network used for every number in the Results table. **If you want to reproduce our results, just `set TSC_TIER=real` and run the pipeline.** No `config.py` edits.

If you want the pipeline on a different city, build a SUMO network yourself:

#### Step 1 — Generate a raw network with osmWebWizard

osmWebWizard ships with SUMO. It's a browser-based tool that downloads a chunk of OpenStreetMap and converts it into a ready-to-simulate SUMO scenario.

```bash
# Windows
python "%SUMO_HOME%\tools\osmWebWizard.py"

# Linux / macOS
python $SUMO_HOME/tools/osmWebWizard.py
```

A browser window opens:

1. Pan and zoom to the area you want, click select area, then drag the **rectangle** around it. Keep it small (a few km² at most) — osmWebWizard's output gets slow to simulate past that.
2. Under **Demand Generation**, tick **Cars** *and* **Left-Hand-Traffic**. (If you skip the second one your network will have no signalised intersections, which breaks everything downstream in this project.)
3. Under the road type tab, select the road required (road up until tertiary were selected in our implementation).
4. Click **Generate Scenario**. It writes a timestamped folder containing `osm.net.xml` plus auto-generated route files.

#### Step 2 — (Optional) Clean up in netedit

osmWebWizard's TLS programs are serviceable but often ugly: redundant phases, weird phase durations, TLS at intersections that don't really need them. If you want to fix that by hand, open the network in netedit (also shipped with SUMO):

```bash
netedit networks/osm.net.xml
```

Netedit's **Traffic Lights** mode (shortcut `T`) lets you edit each junction's phase program. Save with `Ctrl+S`.

Alternatively, skip netedit and let `generate_scenarios.py --regen-tls` rebuild the TLS programs programmatically from a source net. That's what `NetworkConfig.source_net_file` is for.

#### Step 3 — Register the network with `_TIER_NETS`

Copy your final `.net.xml` into the `networks/` folder, then update **one line** in `config.py` — the `"real"` entry of `_TIER_NETS`:

```python
# config.py (top of file)
_TIER_NETS: Dict[str, str] = {
    "grid": str(NETWORKS_DIR / "grid.net.xml"),
    "real": str(NETWORKS_DIR / "my_city.net.xml"),   # <-- this one
}
```

If you also intend to use `--regen-tls`, point `NetworkConfig.source_net_file` at your raw OSM-imported net (the one before TLS regeneration).

#### Step 4 — Regenerate scenarios and run

A new network has different edges, so the existing route files won't work:

```bash
set TSC_TIER=real
python generate_scenarios.py                    # writes scenarios/real/*.rou.xml
python run.py fixed --scenario offpeak --emv         # sanity check on the new net
```
(Note: this is done to generate new routes for cars; the number of cars and traffic intensity can be tweaked under `generate_scenarios.py`)
```python
SCENARIOS = {
    'offpeak':  {'period': '2.5', 'fringe': '2',  'seed': '1'},
    'rushhour': {'period': '0.8', 'fringe': '10', 'seed': '2'},
    'gridlock': {'period': '0.3', 'fringe': '20', 'seed': '3'},
}
```
Then re-train PPO on the new net — **do not reuse a model trained on a different network**. Obs-space and TLS topology are network-specific and the manifest check in `run_ppo_eval.py` will warn if you try.

> **Forcing a non-default network**: if you want to run with a net that isn't either entry of `_TIER_NETS`, pass it explicitly via `Config(network=NetworkConfig(net_file="..."))` in code. Ad-hoc one-offs don't need to live in the tier registry.

## One-command pipelines

There are two pipeline scripts. Each runs every stage (generate → baselines → train → evaluate) in the correct order, on its respective network, and **sets `TSC_TIER` for you** so outputs land in the right tier folder. Use the grid one first, the real-world one once you trust the implementation.

### Grid pipeline (synthetic, fast)

```bat
REM Defaults: scenario=offpeak, seed=42, timesteps=100000 (smaller — grid is easy)
run_all_grid.bat

REM Different scenario / size
run_all_grid.bat rushhour
set GRID_SIZE=6 && run_all_grid.bat offpeak
```

```bash
./scripts/run_all_grid.sh                          # defaults
./scripts/run_all_grid.sh rushhour                 # different demand
GRID_SIZE=6 ./scripts/run_all_grid.sh              # larger grid
```

The grid pipeline regenerates `networks/grid.net.xml` and `scenarios/grid/*.rou.xml` every time, which is the right call — they're cheap to build and you want them in sync with whatever flags you passed.

### Real-network pipeline (Semenyih or your own OSM city)

```bat
REM Defaults: scenario=offpeak, seed=42, timesteps=500000
run_all.bat

REM Different scenario
run_all.bat rushhour

REM Override seed / timesteps via environment variables
set TIMESTEPS=500000 && set SEED=7 && run_all.bat
```

```bash
./scripts/run_all.sh                               # defaults
./scripts/run_all.sh rushhour                      # different scenario
TIMESTEPS=10000 ./scripts/run_all.sh               # quick smoke test
SEED=7 TIMESTEPS=1000000 ./scripts/run_all.sh      # longer run
```

Both scripts are tolerant of partial failures: if PPO training errors out, they still run `evaluate` on whatever baseline output already exists, so you get a partial comparison table instead of nothing.

**First run on a real network**: uncomment the `python generate_scenarios.py` line at the top of `run_all.bat` (or `run_all.sh`). Once scenarios are built, leave it commented so you don't overwrite them on every re-run. The grid script always regenerates, so no equivalent flag is needed there.

## Quick start (individual commands)

Prefer running steps one at a time? Switching tiers is just one env var — no `config.py` edits required:

```bash
# Grid validation pass
set TSC_TIER=grid                                # PowerShell: $env:TSC_TIER="grid"
# Baselines — no EMVs
python run.py fixed       --scenario offpeak
python run.py maxpressure --scenario offpeak

# Baselines with EMVs on road, controller IGNORES them (fair EMV comparison)
python run.py fixed       --scenario offpeak --emv
python run.py maxpressure --scenario offpeak --emv

# Baselines + preemption
python run.py fixed       --scenario offpeak --emv --preempt
python run.py maxpressure --scenario offpeak --emv --preempt

# PPO
python run.py train       --scenario offpeak --emv --timesteps 500000 --seed 42
python run.py ppo         --scenario offpeak --emv
python run.py hybrid      --scenario offpeak --emv          # hybrid always preempts

python run.py evaluate    --scenario offpeak
# Once the grid table looks reasonable, switch to the real net:
set TSC_TIER=real
python generate_scenarios.py
python run.py train       --scenario offpeak --emv --timesteps 500000 --seed 42
# ... etc
```

To watch any run live, append `--gui` to that command.

For the full command reference — including GUI flags, diagnostic switches (`--inspect-emv`, `--debug-preempt`), preemption knob overrides, TensorBoard, and VS Code launch configs — see [`COMMANDS_CHEATSHEET.md`](COMMANDS_CHEATSHEET.md).

## Configuration

Every knob lives in `config.py` as a dataclass. To change a coefficient, either:

1. Edit `config.py` (if you want the new value to be the default), or
2. Override on the CLI: `python run.py hybrid --scenario offpeak --emv --detection-distance 300 --eta-threshold 20`

See `config.py` for the full list of sub-configs: `NetworkConfig`, `ScenarioConfig`, `SimConfig`, `FixedTimeConfig`, `PreemptionConfig`, `RewardConfig`, `TrainConfig`. The `Config.tier` field is set from `TSC_TIER` at construction time, and `network.net_file` is auto-resolved from `_TIER_NETS[tier]` if not explicitly set.

Named presets (`PRESETS` dict in `config.py`):
- `offpeak`, `offpeak_emv` — the default training/eval scenario
- `rushhour`, `rushhour_emv` — heavier demand (untrained policy may regress)
- `gridlock`, `gridlock_emv` — stress test

The same scenario names work on both tiers — `TSC_TIER` alone distinguishes them.

## A note on SUMO teleports

You may see lines like `Warning: Teleporting vehicle 'X'; waited too long (jam)...` scrolling past during dense scenarios — especially `rushhour` and `gridlock`. This is SUMO's `time-to-teleport` mechanism (set to 120 s in `SimConfig`): a vehicle stuck in one spot for more than 120 s is yanked forward to keep the simulation flowing, then re-inserted further along its route via `Vehicle 'X' ends teleporting on edge 'Y'`. The vehicle continues its trip normally and arrives at its destination — the wait just shows up as a chunk of high `waitingTime` and `timeLoss` in the tripinfo.

The `Total teleports` line in our `[fixed]/[ppo]/[hybrid] Tripinfo summary` output therefore counts **vehicles that never completed** (vaporised or still in-network at sim end), not mid-trip teleport events. It will often read `0` even when the console shows hundreds of teleport warnings — that is **not** a bug or a swept-under-the-rug metric. The two numbers measure different things:

- **Mid-trip teleports** (visible in stdout) → manifest as elevated `Mean waiting time` and `Mean time loss` in the summary.
- **Incomplete trips** (the `Total teleports` line) → vehicles that never reached their destination at all.

Under congestion, `Mean waiting time` and `Mean time loss` are therefore the honest indicators of controller performance — not the teleport count. For a direct teleport count, SUMO's own `--statistic-output` produces a `<vehicles teleports="..."/>` block; we don't currently aggregate that, but the raw warnings are visible in stdout if you need them.

## Reproducing paper results from scratch

If you'd rather train from zero (no bundle download), the numbers in the Results table were produced with these exact commands on the Semenyih network (seed 42, 500 k training steps, offpeak + EMV scenario):

```bash
set TSC_TIER=real
python generate_scenarios.py                # first run only
# Baselines — no EMVs (consistency rows)
python run.py fixed       --scenario offpeak
python run.py maxpressure --scenario offpeak

# Baselines with EMVs on road, controller IGNORES them
python run.py fixed       --scenario offpeak --emv
python run.py maxpressure --scenario offpeak --emv

# PPO
python run.py train       --scenario offpeak --emv --timesteps 500000 --seed 42
python run.py ppo         --scenario offpeak --emv
python run.py hybrid      --scenario offpeak --emv          # hybrid always preempts

python run.py evaluate    --scenario offpeak
```

Or, equivalently: `run_all.bat` (Windows) / `./scripts/run_all.sh` (Linux/macOS) — both set `TSC_TIER=real` for you.

Total time on the real net: ~1.5 hours for offpeak, dominated by PPO training. The grid validation pipeline (`run_all_grid.bat`) finishes in about an hour if you just want to verify the implementation works end-to-end.

To first verify the implementation on the synthetic grid, run `run_all_grid.bat` instead — it sets `TSC_TIER=grid` and the network is auto-resolved. No `config.py` switching.
